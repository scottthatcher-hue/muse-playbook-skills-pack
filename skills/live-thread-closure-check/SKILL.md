# Live Thread Closure Check

A handoff summary, a memory entry, a profile note, and a watch's state
file are **caches**. They point you to the source; they are never proof
that an item is still open. The failure this prevents: two items were
carried into a new day as "waiting on the owner" from a handoff summary
and a watch file, when the live threads showed both had been handled
the day before — the document had already been sent, and the newest
message was a thank-you.

## Verify against the live source first

- Open the live thread, inbox, or record that holds the item before
  carrying it into a new chat, a close-out report, a handoff summary,
  or a watch report.
- Read the newest entries in the live source, not only the entry the
  cache was built from — a later reply or action may have closed the
  item after the cache was written.
- State what live source you checked, and when, alongside any item you
  report as still open.

## Run the closure check

- **Who spoke last?** Close the item when the owner was the last to
  speak and no reply is owed.
- **Any outbound after the incoming?** Close the item when an outbound
  message already answered the incoming one the item was based on.
- **Already fulfilled?** Check whether the action the item asks for is
  already done — a document already sent, a connection already made, a
  form already submitted. Prefer the source's own status fields
  (connection state, submission state) over message wording when both
  exist.
- **Just a closing note?** Close the item when the newest message is
  only a thank-you or a casual exchange with no unanswered ask in it.
- Keep the item open only when a specific ask remains unanswered after
  all four checks — and name that ask when you carry the item forward.

## Carry forward only what stays open

- Apply this check **before drafting a reply** for an item, not only
  before reporting it. Drafting for a closed thread wastes the owner's
  attention twice: once on the draft, once on dismissing it.
- Apply it in every surface that re-surfaces open items — close-outs,
  cross-chat handoffs, morning lists — not only in the watch that first
  flagged the item.
- Reconcile with any "acknowledged is not read" rule by running the
  closure check first: a genuinely unanswered ask stays open; a
  superseded draft or a fulfilled ask does not.
- Record the closure evidence in the tracker or watch that held the
  item, naming the live message or state that closed it, so the next
  run does not revive it from the older cache.
- Report a closed item as closed, with its evidence, when the owner
  last saw it as open — instead of silently dropping it or silently
  keeping it on the open list.

## Batch use

Run the check as one batch over every open item in a close-out or
handoff. Stale items travel together in the same cache.

## Worked example

A morning list says: "Recruiter thread — send your résumé (waiting
since Monday)." Closure check on the live thread: the owner sent the
résumé Tuesday 09:38; the recruiter replied that evening; they are now
connected. Verdict: **closed** — résumé sent (Tue 09:38), connection
made; report it as closed with that evidence, and record the closure in
the tracker so tomorrow's list doesn't carry it again.
